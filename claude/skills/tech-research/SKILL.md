# 技術調査(設計・実装の前に行う)

外部の技術を使うとき、**動かし方だけを調べて実装に入ると、古い構成や既定値のまま作り込んでしまう**。
後から品質不足が判明し、作り直しになる。それを防ぐための手順。

> **この手順は一度、出典の存在しない記述を生んだ。**
> 取得に失敗し(403、検索枠の枯渇)、それでも成果物を完成させようとした結果、
> 記憶と検索要約で埋めた記述が「一次情報で確認済」として保存された。
> 以下の規則のうち **★が付いたものは、その事故への対策**である。同種の注意書き
> (「一次情報で裏を取る」)は事故の時点で既に書かれており、効かなかった。
> **効くのは、失敗の倒れ方・検証の主体・依頼の形・責任の分離を変えることだけ。**
>
> **二度目の事故は、引用がすべて本物のまま起きた。**
> 製品の機能の一文ずつ(「入力にできる」「様式を変えられる」「書き出せる」)を集め、
> つないで「その製品が一通りやっている」と結論した。どの出典もそうは言っていなかった。
> 中の作り方(入力 → 中間 → 出力、何が保たれ何が生成されるか)は技術資料に書かれていたが、
> 問いに入れていなかったので読まなかった。引用は文の途中で切られ、限定語
> (「現実の空間の**要素を持つ**世界」)が落ちていた。限界の節には「形をどこまで保つかは分からない」と
> 書きながら、結論と順位づけはそれが分かっている前提だった。
> **◆が付いた規則は、この事故への対策**である。照合は引用 1 件ずつしか見ない。
> **結論(引用をつないだもの)を、要の対象の仕組みと、文脈のない第三者の反証で確かめる。**

## 手順

```
0. 既存の調査記録を確認する
0.5 ★これは実行して測れないか ── 測れるなら調べない
1. 下調べ(広く浅く、短く) ── 何が論点になりそうかを掴む。◆要の対象を挙げる
2. ★観点を提案して合意する ── ここで必ず止まる
3. 本調査(合意した観点だけを深く)── 証拠表を作る。◆要の対象は仕組みを技術資料で読む
4. 成果物にまとめる ── ◆結論の監査表を付ける
5. 効果 ÷ コストで順位づけする
6. 保存する(提案を待たない)
6.5 ★逐語引用を機械で照合する ── 人も LLM も合否を判断しない。◆文の途中で切った引用は不合格
6.7 ◆結論を、文脈のないサブエージェントに反証させる
7. 本実装に入る
```

## 手順0:既存の調査記録を確認する

同じ調査を繰り返すのは高くつく。

- 呼び出し元(プロジェクトの CLAUDE.md、ラッパースキル、依頼文)が調査記録の置き場所を
  指定していれば、**まずそこを見る**
- あれば、**足りない観点だけ**を調べ、同じファイルに追記して調査日を更新する
- **判断基準が変わったなら、前の記録は使い回さない**(「動くか」→「良いか」と目的が変われば、調査はやり直す)

## ★手順0.5:これは実行して測れないか

**手元で測れることを、外部情報で代用しない。**調査を始める前に1回問う。

| 測れるもの | 手段 |
|---|---|
| 入っているソフトの版・オプション・既定値 | `pip show` / `import して print` / `--help` / ソースを読む |
| 自分のデータの性質 | その場で計算する。出力をそのまま貼る |
| ライセンス | LICENSE の実物を開く |

**ドキュメントより実行結果の方が正しい。**しかも安い。
例:ライブラリのある機能が「実装済み」かは、ドキュメントを引用するより
`python -c "import ..."` の出力を貼る方が確実(ドキュメントは未リリース版のものかもしれない)。

測った結果は**出典を要しない**。コマンドとその出力をそのまま記録に貼れば、誰でも再現できる。

## 手順1:下調べ(短く)

目的は結論を出すことではなく、**何が論点になりそうかを掴むこと**。

- 公式ドキュメント、主要な実装、分野の一覧(比較記事、awesome リスト、GitHub のトピック)を数本
- **深追いしない**。「この分野ではここが分かれ目らしい」が見えたら止める
- ◆**要の対象を挙げる。**結論を左右しそうな対象(競合する完成品、採用の候補、
  「既にやっている」と言いそうな製品)を挙げ、観点の提案(手順2)に一緒に載せる。
  要の対象は手順3で仕組みまで読む。広く集めた残りは、機能の一覧で足りる
- ◆**対象を外す判断も、検索の要約でしない。**検索結果に出た候補を「関係ない」と外すときは、本体を開いてから。
  要約の分類(「再構成ではなく生成」など)は出典ではない。外したものと理由は成果物に残す
- 観点を先に提案しようとすると、対象を知らないまま一般論(性能・価格・使いやすさ)を並べることになる。
  かといって本調査の後では合意する意味がない。**掴んだら止める**のがこの手順の役割

## 手順2:観点を提案して合意する(飛ばさない)

**本調査に入る前に、何を調べるかをユーザーに提案して合意を取る。**
調べる観点は対象ごとに違う。固定のリストを当てはめない。

### ◆問いAの答えは、呼び出し元の目的から引く

**問いA(この調査の後、何を決めるのか)を、自分の言葉で書かない。**呼び出し元の目的が書かれた所
(方向性の文書、計画、Issue、依頼文)を読み直し、そこにある言葉を引いて書く。
言い換えると、目的が別のものにすり替わる(例:「VR・AR との体験の違い」→「既にある製品との差別化」)。
すり替わった目的で調べると、引用が正しくても、決めることに答えない成果物になる。

- **既にあるものの意味は、決めることで変わる。**実現の見込みを決めるなら、既にやっている製品は
  見込みの証拠になる。差別化を決めるときだけ、競合として読む
- **検索で見つかる範囲が全てではない。**検索に出やすいのは大手やプラットフォーム。小さな制作者の作例
  (SNS の投稿など)は出にくい。「誰もやっていない」「大手ができている所が限界」と結論しない

### 観点は、対象の性質から導く

次の5つを対象について自問すると、観点が決まる。

| 問い | 答えによって立つ観点 |
|---|---|
| **A. この調査の後、何を決めるのか** | 自作の構成を決める → 構成要素の網羅<br>既製品を選ぶ → カバー範囲・価格<br>入力・やり方を決める → 入力の条件<br>品質不足の原因を切る → 標準構成との差 |
| **B. 良し悪しは測れるか** | 測れる → **品質の基準値**、良い事例の**設定値**<br>測れない → 運用負荷・学習コスト・設計の筋・移行のしやすさ |
| **C. 成果物を外に出すか** | 出す(配布・公開・商用)→ **ライセンス・権利**、出力形式の互換性<br>出さない → ライセンスは観点から落とす |
| **D. 後から変えられるか** | 変えにくい → 移行コスト、共通形式への準拠、ロックイン<br>変えやすい → 深追いしない |
| **E. 一度きりか、運用し続けるか** | 運用する → 更新の活発さ、寿命、保守体制、依存の重さ |

**同じ手順から、対象によって違う観点が出るのが正しい。**
例:3Dの再構成なら「ライセンスの系統」が最重要になるが、社内文書の構造化なら
ライセンスは観点に入らず、代わりに「機密データを外部APIに出せるか」「正解データをどう用意するか」が立つ。

### 提案の形式

```markdown
## 調査の観点(合意してから本調査に入る)

対象:<何を調べるか>
この調査の後に決めること:<問いAの答え>

| # | 観点 | なぜこの対象で効くか | 調べ方 |
|---|---|---|---|
| 1 | | | |

**今回は調べない**:<観点> — 理由:<なぜ外すか>
```

- **観点を左右する前提が依頼文から分からないなら、観点の表と一緒にその前提も聞く**。
  観点は対象の性質から導くが、その性質が分からないことがある(誰が使うか、どんなデータか、
  どこまで外に出せるか、既存の環境は何か)。**3つまで**に絞り、
  **なぜその前提で観点が変わるのか**を1行添える。前提を聞くだけで終わらせず、
  現時点の仮置きの観点は必ず並べて出す
- **観点は5つまで**。増えると合意が形骸化する
- **「調べない観点」を必ず書く**。挙げたものへの同意だけなら流せてしまう。
  外したものを見せて初めて、合意が判断になる
- **常に止まって合意を取る**。短い調査でも例外を作らない
- 調査の途中で観点が変わってよい。ただし**黙って変えず、その場で合意を取り直す**
- ユーザーが観点を追加したら、**なぜ自分から出てこなかったかを1行残す**。
  見落としの型は繰り返す

## 手順3:本調査

合意した観点だけを深く追う。

### 現在の標準は、3つの層で捉える

ライブラリの設定だけを見ると、**土俵そのものが違う**ことを見落とす。3層すべてに目を通す。

| 層 | 調べること | 例 |
|---|---|---|
| **① 入力(データ・機材・粒度)** | 良い結果を出している人は、**何を・どんな品質で・どんな単位で**入力にしているか。専用機材が要るならその価格 | (3D)専用スキャナ、撮影方法 /(文書)元データの形式・解像度・1ファイルが何を指すか /(機械学習)ラベルの付け方、件数 |
| **② 既にある完成品** | 自分が作ろうとしている**全体と同じことをする実装があるか**。**商用に限らず、オープンソースの完成アプリも含む**。◆要の対象は、**中で何をしていて、何が保たれ何が生成・推定されるか、書かれた限界は何か**まで | 市販ソフト、クラウドサービス、機器の内蔵機能、**OSSのアプリケーション**、他人が公開しているパイプライン |
| **③ パイプライン・設定** | 処理の構成と、個別のパラメータ | ライブラリ、手法、設定値 |

- **①は特に見落としやすい**。「自分と同じ入力で、同じ品質が出ている事例はあるか」を必ず確認する。
  あれば差はソフト側、なければ入力側から作り直す必要がある
- **①は「機材」に限らない**。入力データの品質・形式・粒度(1件が何を指すか)も①に含まれる。
  機材が介在しない分野でも、①を飛ばしてはいけない
- **②で最も見落としやすいのが「OSSの完成品」**。商用製品は検索で出やすく、ライブラリ(部品)も
  出やすいが、その中間にある「同じことを一通りやるOSSアプリ」は、部品を探す検索語では出てこない
- **部品ではなく全体で検索する**。「<やりたいこと全体> open source」「<入力形式> to <出力形式> pipeline」
  「<分野> alternative」のように、**完成品を指す語**で1回は検索する
- ③は最新版とその公開時期、置き換えが進んでいる旧方式を調べる

### ◆要の対象は、仕組みを技術資料で読む

「その製品は X ができる」は、機能の一覧(宣伝のページ)から書ける。
**「どの程度・どんな条件で X ができるか」は、仕組みを読まないと書けない。**
結論が要の対象に依存するなら、次を取る。

| 取ること | 何を書くか |
|---|---|
| 流れ | 入力 → 中間(何を経るか)→ 出力 |
| 保たれるもの・作られるもの | 入力から保たれるもの、生成・推定で作られるもの(見えない所、寸法、形など) |
| 書かれた限界・条件 | できないこと、おおまかなこと、条件付きのこと |
| 最新版 | リリースノート、最新版・ベータの資料と、その日付 |

- **探す所**:文書サイトの索引(`llms.txt`・sitemap・目次)、API の資料・OpenAPI、リリースノート、
  FAQ・トラブルシューティング、論文・技術報告。索引があれば**まず索引を全部見て**、仕組みに関わるページを選ぶ
- **宣伝のページ(ブログ・製品ページ・動画の説明・プレスリリース)だけで、程度を書かない。**
  宣伝の文は「できる」を言い、限界を言わない。限界はトラブルシューティングや FAQ にある
- **反証を探す。**結論の候補ごとに、それを否定・限定する記述を 1 回は探す
  (limitations、troubleshooting、not supported、approximate、won't、only、beta など)。
  見つけた限定は結論に書く。探したことは監査表(手順4)に残す
- **最新版を確かめる。**製品は数か月で作りが変わる。要の対象は、次を見る
  - リリースノート(製品の文書の中のもの)
  - **会社のブログ・ニュースの一覧の最新数件**(新しいモデルや次の版は、リリースノートより先にここに出る)
  - 新しいモデル・次の版・ベータが見つかれば、その**開発者向けの資料**(別のドメインのことがある。
    発表の記事のリンクをたどり、「<製品名> beta docs」「<モデル名> API」「<会社名> developer docs」で 1 回は検索する)。
    発表の記事だけで止めない。仕組みは開発者向けの資料にある
- 中身が公開されていなければ「公開されていない」と書く。**公開されていない仕組みを、機能の一覧から推して書かない**

### 採用候補を見るときに毎回確認すること

- 第三者のラッパーやフォークを使う場合、**本家の推奨設定とどう違うか**。
  薄いラッパーは本家の機能の一部しか露出していないのが普通。**使いたい機能が隠れていないか**
- 公開時期、更新状況、利用実績(star 数、issue の様子)
- ライセンス(商用利用、改変物の配布条件)。**フォークに元のライセンスが伝播していないか**を
  LICENSE の実物で確認する(README の表記と食い違うことがある)
- **機能どうしの併用不可の制約**(「AとBは同時に使えない」類は、設計方式そのものを左右する)

### ★証拠表:引用を書けないなら、その主張は書けない

測って得たもの以外の事実には、**必ず3点セット**を付ける。ファイル末尾にこの形で置き、
本文からは `[E1]` のように参照する。

````markdown
## 証拠

```yaml
- id: E1
  claim: 移動は 1〜1.5 m/秒
  kind: 第三者              # 一次 | 第三者 | 推論
  url: https://example.com/guide
  fetched: 2026-09-23
  quote: |
    walk at the pace of a museum stroll, about 1-1.5 m/s
  note: 引用から導いたことがあれば、ここに分けて書く
```
````

- **逐語であること。**言い換えは不可。**引用文を作れないなら、その主張は書かない**
- ◆**引用は文の単位で取る。**文の途中で切らない。文の残りに限定語(only、roughly、
  elements of、inspired by、may、approximately、beta など)があれば、切った引用は意味が変わる。
  どうしても切るときは `partial:` に理由を書く(照合スクリプトは、`partial:` の無い部分引用を不合格にする)
- **`claim` は引用が直接言っていることだけ。**そこから導いたことは `note` に分ける。
  引用と推論を同じ行に混ぜると、飛躍が見えなくなる(「登録率が低いと報告している」→
  「だから別の手法が標準」は、分けて初めて飛躍だと分かる)
- `kind` は3種だけ:**一次**(公式ドキュメント・リポジトリの実物・論文・仕様書)/
  **第三者**(製品ガイド・記事・ブログ)/ **推論**(自分が導いたもの。url と quote を持たない)
- **「推奨 / 標準 / 必須 / 既定 / 効果 大」と書けるのは、引用の中に
  recommend / should / must / default 相当の語があるときだけ**
- **数値は所在まで書く**。「論文 Table 1 の "3DGS-30k" 行、7シーン平均」のように。
  **出典の違う数値を1つの表に並べない**(並べれば読者は必ず比較する)。
  比較するなら「同一表内の比較」と「参考値」を節で分け、本文の要約文にも同じ区別を適用する

### ★取得できなかったものは、出典にできない(失敗は安全側に倒す)

**これが最も重要な規則。**事故はここで起きた。

- **403 / タイムアウト / PDF で本文が取れない / JS 描画 / 要ログイン** → その主張は**書かない**
- **検索の実行枠が尽きた** → そこで**調査を終える**。残りは「調べられなかった」と書く
- **検索結果のスニペットや AI の要約は出典ではない。**URL はページ本体でなければならない
- **「限界」の節に書いて本文には書く、をしない。**取得できなかったものは、限界の節にだけ書く
- ◆**取得の失敗に限らない。**「調べていない」「資料に書かれていない」「分からない」と限界に書いたことも同じ。
  それに依存する結論・順位づけを書かない(手順4の監査表で突き合わせる)

**記憶で埋めない。**取得に失敗した箇所を自分の知識で補うことが、この事故そのものだった。

### ★止め時:「無い」は正常な結果

- **一次情報が見つからない観点は「無し」と書いて終わる。**探し続けない
- **「◯◯のプロトコルを調べて」と頼まれても、そのプロトコルが存在するとは限らない。**
  「公開されていない」が正しい答えであることがある
- 成果物の表に**空欄を残してよい**。埋めるために質を落とさない

## 手順4:成果物にまとめる

**成果物の形は、問いA(この調査の後、何を決めるのか)で決まる。**

| 問いAの答え | 成果物 |
|---|---|
| 自作の構成を決める / 品質不足の原因を切る | **構成の差分表** |
| 既製品を選ぶ | **候補の比較表** |
| 何があるか俯瞰する | **分類と依存関係の地図** |

### ◆結論の監査表(どの成果物にも付ける)

結論の文ごとに、次の表を付ける。**引用 1 件ずつは照合で確かめられるが、結論は確かめられない。**
この表が、結論を確かめられる形にする。

| 結論 | 直接言っている証拠 | つないだ推論(どの証拠から何を導いたか) | 依存する限界・未確認 | 探した反証と結果 |
|---|---|---|---|---|
| | [E3] | 無し | 無し | 「limitations」で検索、無し |

- **2 つ以上の証拠をつないだ結論は「推論」と書く。**本文の結論の文にも「(推論)」と付ける
- **「一通り」「すべて」「既に解決」「完成している」など、網羅・完成を言う語は、
  それを直接言う出典か測定が無ければ使わない**
- 「依存する限界・未確認」の列が空でない結論は、**弱めるか、その点を調べてから書く**
- 「探した反証」の列が空の結論は、まだ書けない

**いずれも、列は合意した観点にする。**観点を合意してからその観点を列にすれば、
記録の形式は対象ごとに正しく変わる。形式を先に固定すると、対象に合わず破られる。

### 構成の差分表(自作の構成を決める / 品質不足の原因を切る場合)

目的は**「標準構成に対して、自分の実装に何が欠けているか」を特定すること**。数値の比較ではない。

| 層 | 標準構成の要素 | 何のための要素か | 自分の実装 | 差分 | 効果 | コスト |
|---|---|---|---|---|---|---|
| ① 入力 | (例)入力の品質・粒度の要件 | 何のために必要か | いま用意できているもの | **入力差** | 大 | 代替手段の有無 |
| ② 完成品 | (例)同等の機能を持つ既製品・OSS | 作る価値の判断材料 | 自作 | **要判断** | - | 自作する理由を明文化 |
| ③ 設定 | (例)構成要素・パラメータ | 何のために必要か | 現状 | **未対応** | 中 | 小 |

- 標準構成の要素は**漏れなく列挙する**。「あると良いもの」ではなく「良い結果を出している実装が
  共通して持っているもの」を並べる
- 「対応済み」も書く。どこまで届いているかが分かる
- **自分の実装がまだ無い場合**は、「いま想定している素朴な作り方」を仮置きして埋める
- **入力差(機材・データ品質・粒度)は、ソフトや運用で埋められるかを必ず書く**。
  埋められないなら、その前提で目標を下げる
- **差分の一覧が、そのまま改善の計画になる**

ベンチマークでの検証は、この差分表を作った後の**任意の確認手段**。
差分を埋めても結果が改善しないときに、実装の正しさを疑うために使う。

### 判断の物差し

**「何をもって良しとするか」を先に決める。**基準がなければ、出たものの良し悪しを判断できない。

- 測れる対象なら**数値**(精度、処理できた割合、所要時間、費用)。公開ベンチマーク・製品の公称値・
  論文の報告値を探す
- **測れない対象なら判断軸**(運用負荷、学習コスト、移行コスト、寿命)。無理に数値を作らない
- **物差しは1つとは限らない**。項目ごとに難易度が違うなら、項目別に決める
- ただし**ベンチマークで競うことが目的ではない**。物差しは「自分の結果が妥当か」を判断するためのもの
- **公開の基準値が自分の条件と離れている場合**(理想的な入力で測られている、規模が違う)は、
  その差を明記したうえで**自分の初回実行の結果を基準線にする**。以降はその値からの改善幅で判断する

## 手順5:順位づけする

差分・候補を**効果 ÷ 実装コスト**で並べる。これが改善計画になる。

## 手順6:保存する

- **会話の中にしか無い状態を作らない。受け取った時点で保存する。提案を待たない**
- 保存先は**呼び出し元の指定に従う**(プロジェクトの CLAUDE.md、ラッパースキル、依頼文)。
  指定が無ければユーザーに聞く
- **サブエージェントに調査を委託した場合も、結果を受け取った側が保存する**。
  委託先に「ファイルを書くな」と指示したなら、その分は自分で書く
- 調査日と出典(URL)を必ず残す
- 実装の判断が調査のどこに基づくかを、コードのコメントか記録に残す

---

## ★手順6.5:逐語引用を機械で照合する

**検証する主体が LLM である限り、「確認した」と書けてしまう。**だから合否は
決定的なプログラムが出し、**LLM も人も「確認した」と宣言しない**。

- 調査結果は、まず**未検証の置き場**に保存する(会話の中にしか無い状態も作らない)
- 照合スクリプトが `(url, quote)` を取得・正規化して部分一致を取る
- **全行が一致したときだけ**、正式な置き場へ移す。**昇格を LLM に判断させない**
- **照合不能(403・PDF・JS描画)は不合格**として扱う。通すなら人が個別に見る
- スクリプトが出す「要人確認」(一次を名乗るのにドメインが業界誌、強い主張なのに
  引用に裏づけの語が無い)は、件数が少ないうちは全部見る

- ◆**文の途中で切れた引用は不合格**(`partial:` に理由があれば合格にして要人確認に出す)。
  スクリプトは文全体を表示する。**文全体を読み、claim がその文の限定語と食い違っていないかを見る**
- **要人確認の「一次を名乗るがブログ系の出典」を流さない。**会社のブログは会社の主張で、
  機能があることの根拠にはなるが、程度・限界の根拠にはならない

呼び出し元がスクリプトの場所を指定していればそれを使う。無ければユーザーに聞く。

## ◆手順6.7:結論を、文脈のないサブエージェントに反証させる

**結論を書いた本人は、結論を支える読み方で出典を読む。**だから結論の確かめは、
結論に至った文脈を持たない第三者に任せる。

- 渡すもの:結論の文と監査表、証拠表(URL と引用)。**調査の経緯・自分の見立て・期待する答えは渡さない**
- 問いの形:「次の結論それぞれについて、出典(と、同じ製品・技術の公式の資料)から、
  結論を否定する・限定する・条件を付ける記述を探せ。逐語で引け。無ければ『無い』と返せ。
  『無い』は正常な結果である」
- 返ってきた反証は、照合スクリプトにかけてから結論に反映する。反映したら監査表の「探した反証」に書く
- 要の対象に依存する結論は必ず。残りは、件数が多ければ順位づけに使う結論だけでよい

## ★委託するときの規則

サブエージェントに調査を任せると、**ユーザーと対話できず、途中で止まれず、
ツール枠が尽きても完成品を返すことを期待される**。この構造下で最も合理的な振る舞いは
「知っていることで埋める」になる。**注意書きではなく、依頼の形と評価軸を変える。**

- ◆**「何があるか」だけを問わない。**要の対象には、「中で何をしているか(入力 → 中間 → 出力)」
  「何が保たれ何が生成・推定されるか」「書かれた限界」「最新版・ベータ」を問いに入れる。
  機能の有無だけを問えば、機能の一文ずつが返ってきて、それをつないだ結論が飛躍する
- ◆**件数の目安を出さない。**「30 件前後」は広さを求め、深さを削る
- ◆**結論を左右する出典は、呼び出し元が自分で通して読む。**委託の証拠表は引用の断片で、
  その文の前後や同じ資料の別のページ(限界・FAQ)を含まない
- **問いの形を変える。**「◯◯のプロトコルを調べて」ではなく
  「**◯◯は撮影の数値ガイドを公開しているか。していなければ『無い』と返せ。『無い』は正常な結果である**」
- **判断を委託しない。**委託の成果物は**証拠表だけ**。「効果 大」「標準」「そのまま採用する」
  「順位づけ」は書かせない。それは呼び出し元がユーザーと決める(手順4〜5)
- **取得に失敗したら、そこで返させる。**「限界」の節に書いて本文は完成させる、をさせない
- **受け取った側は、まず『限界』『未確認』の節を読む。**そこに取得失敗や枠切れが
  書かれていたら、**本文も信用しない**。事故はここを読み飛ばして起きた

## やってはいけないこと

- **観点を合意せずに本調査へ入る**。何を調べるかがずれたまま深く掘ると、丸ごと無駄になる
- **「動いた」で調査を終える**。動くことと、良い品質が出ることは別
- **部品(ライブラリ)だけを探して、全体の先行事例を探さない**。「同じものを既に作っている人が
  いないか」を必ず1回は検索する。これを飛ばすと、既存実装と同じものを作り直すことになる
- **設定の層(③)だけを比べる**。機材や入力(①)、既にある完成品(②)の差を見落とすと、
  埋められない差をソフトで追いかけ続けることになる
- **物差しを持たずに本番規模の処理を始める**。結果を評価できない
- **ラッパーの既定値を確認せずに使う**。既定値は本家の推奨と違うことがある
- **記録の形式を先に固定して、そこに調査を押し込む**。形式は観点から決まる
- ★**取得できなかった情報を、記憶や検索要約で補う**。これが実際に事故を起こした
- ★**「限界」に取得失敗を書きながら、本文はその話題を埋める**
- ★**委託先の成果物を、限界の節を読まずに保存する**
- ★**引用が言っていないことを、引用の横に書く**(引用は本物なのに主張が飛躍する型。
  機械では検出できないので、`claim` と `note` を分けて自分で見るしかない)
- ◆**機能の一文ずつをつないで、「一通りやっている」と結論する**。つないだ結論は推論で、
  要の対象の仕組みを読み、反証させるまで書けない(監査表・手順6.7)
- ◆**文の途中で引用を切って、限定語を落とす**
- ◆**宣伝のページだけで、程度・限界を書く**
- ◆**限界に「分からない」と書いたことを、結論や順位づけの前提にする**

## 結果が期待に届かなかったとき

パラメータを触る前に、**構成そのものが現在の標準か**を疑う。
そのうえで、**観点が間違っていなかったか**に戻る(見ていた軸が的外れだった可能性がある)。
